# DD-claw

一个运行在你自己电脑上的主播动态监听与推送工具：盯住你在意的 B 站主播（直播状态、B 站动态、微博），自动判断每场直播「是什么内容」，再按你定的规则把消息推到 QQ 群、QQ 私聊或 Windows 系统通知。

设计前提是**多主播、长时间挂机**：关注列表上百人、高峰几十人同时在播，它持续追踪状态而不是一次性提醒，所有规则都在本地控制面板上点选完成，不需要碰配置文件。

## 它能做什么

- **开播通知**：批量轮询直播状态，谁开播了立刻知道，带上标题、分区、封面图。
- **动态与微博归档**：监听对象的 B 站动态和微博时间线持续抓取存档，面板里按主播混排展示最近动态。
- **内容分类**：每场直播自动归类——「歌回」「3D 回」「生日回」……分类口径完全由你定义：填关键词/分区条件走确定性匹配，写一段自然语言提示词走 LLM 判断（可配多模态模型看直播画面），两者可以写在同一条分类里。
- **按规则推送**：推送规则 = 哪些主播 × 哪类内容 × 推到哪个渠道 × 用什么推送词。比如「阿梓 + 歌回 → QQ 群：阿梓唱歌速来」「全部主播 + 歌回 → QQ 私聊」。多条规则同时命中时各自生效，同一个渠道只推一次，推送词取优先级最高的那条。
- **NapCat 托管**：自动维护 NapCat（QQ 机器人）的专属端口条目、进程看门狗挂了自动拉起，QQ 侧不需要你手动管。

## 它是怎么工作的

整个工具分三段，各自独立：

**1. 抓取**——持续轮询 B 站直播状态（匿名即可，永远在线）；扫码登录 B 站后追加关注列表同步和空间动态抓取；扫码登录微博后追加微博时间线。抓到的原始数据全部进本地 SQLite 存档，状态变化（开播、下播、新动态）变成信号发给下一段。

**2. 分析**——每场开播做一次内容分类：填了 LLM 提示词的分类优先问模型（把你写的提示词逐条交给它判断，可附带直播画面截图）；LLM 没配置、挂了或超时，自动退回关键词/分区的确定性匹配，分类和推送链路不会因此中断。没填提示词的分类永远走确定性匹配，完全不依赖 LLM。分类结果连同依据（命中的关键词，或模型给的判断理由）入库存档。

**3. 推送**——分类结果对照你定义的推送规则，命中即组装消息发给对应渠道。推送之前还有一层确定性护栏：每场直播只推一次、被静音的主播不推、推送总开关可以一键全停（追踪和分类照常）。

LLM 是**可选增强**，不是必需品：没有 LLM 时关键词/分区规则照常工作；LLM 只负责「这场直播是什么内容」的客观判断，推不推、推去哪永远由你写的规则决定。

## 上手

需要 Node.js 22 以上；QQ 推送需要 Windows 版的 NapCat（本机系统通知不需要）。

```bash
npm install
npm run build
node dist/index.js
```

首次启动后打开控制面板 <http://127.0.0.1:8787>（只监听本机），之后所有配置都在面板里完成：

1. **登录**：在「监听」卡片里扫码登录 B 站（关注列表 + 动态）和微博（可选）。不登录也能用，直播状态监听不依赖登录。
2. **加主播**：B 站登录后关注列表会自动同步成候选池，点头像一键加入监听；监听后主播卡片实时显示直播状态和最近动态。
3. **定义分类**：在「分类规则」卡片新建分类，比如「歌回」——填关键词（唱、歌回）和分区（虚拟Singer），或者写一段 LLM 提示词描述这类直播的典型特征。
4. **定义推送规则**：在「推送规则」卡片新建规则，选分类（或「任意开播」）、勾选生效主播（不勾 = 全部）、选渠道、填推送词。规则可以拖拽排序，顺序决定同一渠道推送词的取舍。
5. **QQ 推送**：在「NapCat」卡片填 NapCat 一键包路径和机器人 QQ 号，点「计划任务」授权一次，之后进程由看门狗托管；在「推送渠道」卡片添加 QQ 群/私聊渠道。

开发期用 `npm run dev`（改动自动重启）。常用验证命令：`npm run probe`（测一次开播状态接口）、`npm run probe-llm`（测 LLM 接入）、`npm run test-notify`（假消息走完整推送链路）。

## 数据存在哪 / 迁移

所有面板设置和历史数据都在项目目录里，换机器迁移带走这三样即可：

- **`data/dd-claw.db`**（含 `-wal`/`-shm` 伴生文件）——全部面板设置（监听名单、分类与推送规则、渠道、LLM provider 与 key、NapCat 与高级设置）+ 历史数据（直播场次时间轴、分类判定、动态/微博存档、推送日志）。
- **`cookies.json` / `weibo-cookies.json`**（项目根目录）——B 站 / 微博登录凭据。不带也行，到新机器上面板重新扫码即可。

可以不带：`config.json`（只剩面板端口等自举项，缺省自动用默认值）、`.env`（只剩数据库路径与日志级别，缺省即可）、`data/cache/`（通知图片缓存，自动重建）。

## 隐私与边界

- 全部数据只存在本地：设置与历史数据在 `data/dd-claw.db`，登录凭据在项目根的 `cookies.json` / `weibo-cookies.json`，不上传任何服务器；LLM 请求只发往你自己配置的接口地址。
- 对 B 站和微博**只读不写**：不发弹幕、不点赞、不评论，所有抓取走公开页面/接口加你自己导入的登录凭据。
- 扫码登录的 cookie 用于接口调用，绝不写入日志。

## 当前状态与已知限制

- LLM 分类管线已接通（提示词、多模态画面输入、失败回退、结果入库），但分类效果未经大规模实测，建议先给个别主播开「LLM 分析」开关试用——该开关在主播详情里，默认关闭。
- LLM 的画面判断目前只能用封面/关键帧截图；「弹幕内容」类特征（比如提示词里写弹幕打 call 词）还没有输入来源，弹幕抓取是后续计划。
- 直播中途改标题不会触发重新分类；直播中抽查、预告时间表（从动态/微博提取时间）在路线图上。
- 分类结果（verdicts）已入库，但面板还没有专门的展示页。

更深入的架构设计见 `docs/design.md`，接口能力边界与踩坑记录见 `docs/boundaries.md`。
