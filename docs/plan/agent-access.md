## 产品目标

| # | 目标 | 含义 |
|---|---|---|
| G1 | **一个能力面，N 种接线** | 「查数据 / 改设置」的全部能力只在注册表定义一次；Web UI、/mcp、WebUI Agent、MaiBot 插件、NapCat 直连都只是接线方式，任何途径不得绕过注册表私接 Db |
| G2 | **QQ 渠道自助** | 群 / 私聊成员用自然语言管理**本渠道**的推送；每个渠道只能看到并只能改自己，群号与个人 QQ 号无区别 |
| G3 | **主人全局管理** | 本机即主人：面板、Claude Code、WebUI Agent 都是 admin，可改全局；QQ 入口（含主人私聊）不设 admin |
| G4 | **写操作彻底可撤销** | 每个单次变更可撤销，栈式逆序、历史全量保留——这是「写前确认不强制」的唯一兜底 |
| G5 | **聊天体验一致，权限按来源分层** | 聊天式输入在各入口反馈一致，接入途径与 loop 归属是实现细节；权限不因入口统一：QQ = 来源渠道自助，本机 = admin |

产品边界决策（已定，不再翻案）：

- **写前确认不强制**：面板可切「写前询问 / 自动修改」，QQ 侧由模型追问 + 口头确认；安全重心在**可设置面的权限**，不在单次修改的管控。
- **提示词注入是可接受的理论风险**：最坏结果 = 本渠道成员给本渠道加/删规则——正是开放的能力本身；写可回退即可控，不做结果隔离标记 / 写工具白名单等重防护。
- **上下文的持久与裁剪**：会话落库、单会话 + 重置；不自动裁剪（面板提示用量，QQ 侧见「渠道隔离」的配套政策）。
- **触发纪律**：确定性命令与自然语言两条路共存、可同时启用，斜杠不是降级替代。

## 接入途径与关键选择

| 途径 | Agent Loop 归属 | 身份锚点 | 角色 |
|---|---|---|---|
| Web UI（REST） | 无（表单直调） | localhost 绑定 | admin |
| MCP | 入口自带（Claude Code 等 Host） | Bearer token | admin / gateway |
| WebUI Agent | DD-claw 提供 | localhost 绑定 | admin |
| MaiBot 插件 | 入口自带（MaiBot） | Host 注入的 group_id + 渠道绑定令牌 | gateway |
| NapCat 直连 | DD-claw 提供（或确定性命令，无 loop） | OneBot 事件 user_id/group_id | gateway |

**为什么 QQ 有两条路、怎么选**：两者解决同一个问题（群/私聊对话入口）。MaiBot 持续用 LLM 监听群聊时走插件（DD-claw 零常驻）；想绕开 MaiBot 自己的对话行为（不借它的 loop 与触发判定）就走直连。直连的信任链最短（事件身份不经 LLM），代价是 DD-claw 自己收消息、自己做触发与限流。确定性斜杠命令两边都能做，**不构成选择理由**。

## 信任模型

**只在接入层确权，能力层只认 role + 调用域**；`channelId` 这类身份字段永不进工具 schema。锚点与角色的对应见 [mcp.md](../mcp.md)「角色与权限」/「为什么不信工具参数」，鉴权口径（`/mcp` 永远要令牌、只有 `/api/*` 回环免 token）同见该文。

### 能力层调用域（scope）

```
runTool(deps, def, args, ctx)     // ctx = { role, name, scope: { channelId?: number } }
  → zod 校验 args →（写操作）快照 + 审计 → def.handler(deps, args, ctx) → 错误归一为中文文案
```

`scope` 是「这次调用属于哪个调用域」的唯一表达，读 / 写 / 撤销 / 审计 / 限流共用它；进程内入口由接入层构造，`/mcp` 由**令牌绑定**解析。

**方案 A：令牌绑定渠道（采用）**。`mcp_tokens` 条目带可选 `channelId`，服务端由 token 解析 scope；一个来源渠道一条令牌，同渠道多令牌允许（轮换用），admin 令牌不带渠道。顺带同源解决四件事：按渠道限流分桶、审计带渠道、读侧服务端裁剪、写范围校验。

**方案 B：渠道留在 arguments、由插件在 `tools/call` 前强制覆盖（否决）**。理由：那样能力层信任的就是「参数里的身份声明」，隔离退化为「插件不做错就没事」，任何参数生成链路一坏就全线失守。方案 A 的代价是参数形状的破坏性改动（`channelId` 从工具 schema 移除），gateway 契约表述为「工具名与业务参数不变，身份参数改为 scope 注入」。

## 写操作快照与撤销（G4 的落地）

**快照选型：表级前像快照 + 差分**，而不是让每条写路径自己声明「影响了哪些行」。理由：删分类级联停用 N 行、排序整表重写、新建取 `MAX+1`、settings 的删除式写、provider 复合写两行——这五种形状在差分下**收敛成同一种记录**，且顺带拿到后像（撤销插入/删除才做得出来，只记前像做不出）。代价是每次配置写整表 SELECT 一遍；只发生在配置写路径，配置表几十到几百行，绝不进轮询循环。

**实际取舍（与「与写入同事务」的字面差别）**：引擎有一个同步事务版 `capture()`（读前像 → 写 → 读后像 → 落记录全在同一事务）。但写工具的 handler 可能含 await（校验、网络探测），而 better-sqlite3 的事务不能跨 await，所以**写工具实际走 `track()`**：

- 前像读取**不在**事务内；改用内部队列把走 track 的写**串行化**，保证差分窗口不被另一个写工具交错。
- 「写 → 读后像 → 差分 → 落记录」在 handler 返回后是连续同步代码，单线程下实际原子。
- 残留窗口只有一个：**记录写入自身失败**（磁盘级故障）——此时写已提交而记录没落，方向是「写了却撤不掉」，错误会抛给调用方，不会静默。
- 不走 track 的写（轮询源回写游标/头像）可能落在差分窗口里；混合表（`streamers` + 三张图文账号名单）用**忽略列**把这类轮询列排除在差分、比对与还原之外，既不凭空产生记录，也不让撤销无故中止。忽略列清单的唯一信源在 `src/core/undo.ts`。

**撤销语义**：

- **比对的是后像**：撤销前逐行比对「记录里的**后像** == 当前值」（只看非忽略列），相等才用前像还原；不等则中止且一行不动（宁中止不丢写）——这是「该设置已被其他入口改过」的判定，UI 要标成预期结果而不是故障。
- **栈式逆序、每调用域一栈**：只撤最近一次、可连续撤销、不跳序；admin 有全局栈，每个 QQ 渠道各有自己的栈，撤销只作用于本域。
- **撤销本身是写路径**：撤完按「表/键 → 回调」触发热生效（等同面板手改），回调闭包只在装配根；撤销自身 `track: false`，不进变更记录。
- **归档表不参与撤销**：轮询与源自动写的表（会话/帖子/判定/时间轴等）不进变更记录。

#### 变更记录遗漏面（本期不入撤销）

覆盖范围只是 settings / 配置表类写入。以下写面**明知而未纳入**，避免误以为全都可撤：

| 写面 | 兜底方式 |
|---|---|
| B站 / 微博凭据落盘（扫码后 merge 写文件） | 与 LLM key 同口径视为隐私例外；要「撤销」就重新扫码或清空文件 |
| NapCat 托管配置写盘与计划任务启停 | 面板卡片 + 看门狗自愈；改错可重配或手工恢复文件 |
| 媒体与通知缓存（关键帧、toast 图、平台 helper） | 纯缓存，删掉即重建 |
| 一次写库脚本（`migrate-*`） | 幂等，不属于面板 / 对话变更 |
| 对外副作用（测试推送、`--test-notify`） | 不可撤回，仅验证动作 |

若将来要撤销这些，凭据与 NapCat 配置需要额外的**文件前像**快照，成本另估。

## 渠道隔离（G2 的落地）

隔离的锚点只有一个：**来源渠道 = 令牌绑定的 `scope.channelId`**，七处都在服务端强制，不靠前端/插件过滤——① 会话→渠道映射查不到就拒绝服务；② 读侧按 scope 裁剪后才离开能力层；③ 写经调用域注入、范围限本渠道（多渠道规则先拆分）、删除校验归属；④ 会话键 = 来源渠道，上下文互不可见；⑤ 撤销只及本渠道栈；⑥ 审计带渠道、限流按渠道分桶；⑦ 系统提示声明只处理本渠道。实现与逐条强制见 [mcp.md](../mcp.md)「gateway 写/读的服务端强制」与 [src/qqbot/AGENTS.md](../../src/qqbot/AGENTS.md)。

**QQ 侧配套政策**：上下文**不自动裁剪**（面板同样不裁剪，只提示用量），会话达阈值时由回执末尾主动提示 `/reset`；回执按 QQ 限制裁剪，正文优先、超长改「已写入，详情请在面板查看」。阈值成因与现值见 [modules/qqbot.md](../modules/qqbot.md)，长度阈值仍属「待定项 2」。

## 多渠道规则：copy-on-write 拆分

自助要改的规则推**多个渠道**时先拆：原规则保留其余渠道、内容一行不动（`createdBy` 原样），另建一条只含本渠道的规则（`createdBy='mcp'`），后续写只操作拆出来的这条，拆分与后续写同一事务。原规则本就只剩本渠道时就地操作；**非 mcp 规则也只允许「移出本渠道」**，不得整条删除（否则会误伤 admin 配的其它渠道）。原语与约束见 [src/mcp/AGENTS.md](../../src/mcp/AGENTS.md)。

## 统一会话与 UX 一致性（G5 的落地）

两处实质差异不该让用户看到两套行为：**loop 归谁**（Claude Code / MaiBot 自带；WebUI Agent 与 QQ 直连共用 DD-claw 的同一个 loop；确定性命令不需要 loop）与**权限层级**（QQ = 本渠道；本机 = admin）。其余要素必须同源：结果与错误文案都过 `runTool()`；撤销是内部工具 + 面板变更历史；写前询问按入口各自呈现但共用同一写模式设置；会话与权限同源隔离。

## 实施依赖与分期

P0 是**共享地基**（执行器 + 调用域 + 快照/撤销 + REST 收敛），与聊天 UI 无关；P1 缩回「loop + 聊天视图」——P2 的正确性不该绑在 P1 的 UI 进度上。P2 与 P3 可只做其一也可并存，互不依赖。

### P0：地基（不依赖任何新前端）

交付判据：

1. 面板侧任一次配置写（含排序、级联停用）都能在设置页底部看到并撤销；
2. 撤销后像与当前值不一致时中止并提示；
3. 面板 REST 不再有绕过注册表的直接 Db 写；
4. 启动日志明确「`/api/*` 回环免 token = admin；`/mcp` 必须带 Bearer」；
5. **`/api/*` 响应形状与状态码不变**（前端契约保持，webui 无回归，`webui/demo/mock-api.js` 同步）；
6. **撤销路径触发热生效回调**（撤运行时参数 / 监听开关 / provider 均与面板手写等价）。

### P1：agent loop + WebUI Agent

验收口径（判成败的硬门槛）：

| 项 | 门槛 |
|---|---|
| 用例集 | ≥ 20 条本机自然语言请求，覆盖读 / 写 / 撤销 / 能力边界四类，落 `src/agent/` 下的用例表 |
| 工具选择正确率 | ≥ 90%（选对工具；多步任务按最终结果判定） |
| 参数正确率 | ≥ 90%（uid / id / 开关值不编造；不确定时先调 `search_streamers`） |
| **误写率** | **0 容忍**——「写前询问」模式下未经用户确认的写操作数为 0（「自动修改」模式下不确认即写是**合法行为**，不计误写）；出现一次即修系统提示与工具 description |
| 能力边界 | 100% 不臆造：不存在的 uid / id 必须报错或澄清，不得凭空构造 id（本机 admin 下「改任意渠道」是合法业务，不算越界） |
| 失败处置 | 任一项不达标 → 先调 description / 提示词；两轮仍不达标 → P1 暂停，回到 P0 评估是否值得继续 |

**仍未验证**：`completeChat` 的 responses 分支（`function_call_output` + `call_id` 往返、`instructions` 与 `tools` 能否共存）只有离线测试；第一次接真端点时先跑一次单轮工具往返再放量。上表全部条目需要人在面板上跑，属验收实操项。

### P2：MaiBot 插件

插件是独立仓库（Python），DD-claw 侧只保证 gateway 契约稳定（工具名与业务参数不变、身份经 scope 注入）。设计依据、定案理由与复核项见「P2 详案」。

### P3：NapCat 直连

前置 = 决定绕过 MaiBot（或 MaiBot 不监听群聊）。复用 P0 地基与同一个 loop；确定性命令与 LLM 对话两条路共存、可同时启用。触发纪律、会话映射、限流与回执策略见 [modules/qqbot.md](../modules/qqbot.md)。

### 配置写路径缺口清单

清单的**机械信源是 `src/panel/write-path-inventory.test.ts`**（从 `server.ts` 提取写路由 × 工具名，新增未分类的写路由直接测试失败）。本文只保留分类口径与排除理由——手抄路由表必然过期，不要再维护第二份。

| 分类 | 含义 | 现状 |
|---|---|---|
| `registry` | 写路由经注册表工具，获得校验 / 审计 / 快照 | 面板全部配置写已收敛于此 |
| `excluded` | 明知不进撤销覆盖的写面，或对话入口自身的消息写 | 凭据落盘、NapCat 配置与进程、扫码登录流（含带写副作用的 poll GET）、测试推送与外部副作用；`POST /api/chat` 与 reset 只写会话消息 |
| `executor` | 撤销执行器本身（`track: false`） | 机器校验其工具必须 `exists + write + track === false` |

**两个概念必须分开**：① **回滚覆盖**——配置写路径全部过注册表，撤销才彻底可信；② **工具暴露**——哪些进 LLM 工具面。①决定②的实现位置，但不等于②全开放：排序、测试推送、写模式开关都是「①成立而②暂关」。

REST 收敛时对工具语义做的对齐（additive，MCP 契约不破坏）：`set_streamer` 收 analyze/notify、LLM provider 收 keyEnvs、X 账号新建并入存在性校验（not-found 拒、链路原因照收、成功种入昵称）。两处分歧的裁决：provider 重名——**REST 保持「重名 400」，工具保持按名 upsert**，路由在调工具前做预检；`set_streamer` 的微博昵称解析**只在工具侧保留一份实现**。

## P2 详案：MaiBot 插件（QQ 自助推送）

**硬边界**：每个群 / 每个私聊只能看到并只能改与自身相关的推送配置；QQ 入口（含主人私聊）一视同仁，不设 admin。「本群」一律理解为消息来源渠道。

**为什么 MaiBot 不直连 MCP（定案）**：

1. **MaiBot 的 MCP 连接是进程级共享**：所有聊天流共用同一条连接，配置在全局 `bot_config.toml` 的 `[mcp]` 段，没有任何按群划分的字段——服务端 scope 最多覆盖全部群的并集。这正是插件用自带 httpx 客户端逐群选令牌的原因（方案 A 可行的前提）。
2. **工具参数全部由 LLM 生成**：任何自报群号的字段都可被 prompt injection 伪造，不能作信任锚点。

可信的群身份只有 OneBot 事件里的 `group_id`。Host 在工具回调路径注入 `{stream_id, chat_id, group_id, user_id, platform}`，插件不必自建事件层；但注入是 **fill-only**，所以不变量是「这些身份字段永不进工具参数声明，只读运行时 kwargs」。否定的是「MaiBot 作为 MCP Host 直连」，插件本身仍消费 `/mcp`，端点形态不变。

**插件契约要点**：`[[groups]]` 里配「哪个群用哪条令牌」，令牌与渠道的绑定关系只存在 DD-claw 侧（`mcp_tokens`），`channel_id` 不发给 DD-claw、不进任何工具参数；对 LLM 暴露三个动作（加本渠道推送、删本渠道推送、查本渠道推送），都标 `core_tool=True`（MaiBot 默认放 deferred 池）；业务错误的中文文案直接透传回群。

**复核项（随 MaiBot 版本升级重看）**：

- `@Action` → `@Tool` 兼容转换后，legacy 的强制覆盖语义是否仍生效（决定身份注入要不要加保险）。
- 文档声称工具回调有 `message` kwarg，源码里只有 command 路径有——触发判定别依赖它。
- httpx 直连 `/mcp`、`data:` SSE 帧解析（含是否先 `initialize` 一次兜底）。
- 上游若改注入字段或工具池语义，本节的信任模型推论要复核。
