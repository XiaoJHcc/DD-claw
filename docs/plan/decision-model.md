# 决策模型接入路线

> **状态**：M1 管理面、M2 判定契约、M3 图片管线、M4 决策档已落地；LLM 与决策档的实战验收未做。进度只查 [status.md](../status.md)。
> 本文件保留**协议选型、判定契约、分期与验收合同**；外部证据与时效性结论见 [research/decision-models.md](../research/decision-models.md)。

## 一、已定路线

1. **协议只做 System One**：`POST <baseURL>/systemone`，请求 `state + questions`（含图时另带顶层 `assets`），响应同 id 的 typed answers。
   - `protocol` 枚举只有 `systemone`；`/v1/decisions` 形状不同，真正接入时再加枚举值与适配分支，不把厂商字段带进业务代码。
   - 原语只接 `choice` / `noul`；`score` 留在线格式里不用，`box` 不接。
   - baseURL 写到版本根这一层（`/v1` 可省，适配器按需补默认 `v1`），适配器追加 `/systemone`。
2. **模型版本写死**：生产配置用 `jev-1.14.0` 这类完整版本号；审计记响应回显的 `model`。
3. **通道隔离**：独立 settings（`decision_providers` / `decision_key:<name>` / `decision_*` 参数）、独立 key 池、独立熔断；不与 `LlmRouter` 共享任何运行时状态。
4. **识图是默认输入**：带图内容只交给标记了 `vision` 的决策供应商。纯文本供应商是最低兼容：可以判，结果落库，但对带图内容不作为生效结论。
5. **直接实战，不做标注与离线标定**：阈值是 settings 里的可调参数，按线上审计回看调整；判得准不准由主人在内容记录里看。
6. **选型不等于选榜单**：Jev 只是参考实现。换模型 = 在面板改供应商，阈值按需重调。

## 二、判定契约

### 2.1 两种判定

| | 是非判定 | 主分类 |
|---|---|---|
| 回答 | 这条内容属不属于分类 X（允许重叠） | 这条内容最像主分类组里的哪一个 |
| 参与分类 | 本内容类型下全部启用分类 | 本内容类型下勾选了「主分类」的启用分类，另加「其他」 |
| 消费者 | 推送规则匹配（不变） | 时间表等展示 |
| 确定性条件 | 条件组命中 / 未命中 | 按分类排序取第一个「生效且属于」的组内分类 |
| LLM | `{match, evidence}` | 选一个分类 id 或「其他」 |
| 决策模型 | 简单模式每分类一道 `noul`；精确模式每原子条件一道 `noul` | 一道 `choice`，得各项概率分布 |

两种判定互不约束：主分类与是非结论可以不一致，推送永远只看是非结论。**备选** = 主分类组里、是非生效结论为「属于」的其他分类。

LLM 不输出概率或置信度（自报数字没有校准意义）。简单模式的 `confidence` 承载决策模型的 `p`；精确模式不把逐条件概率合成最终概率，`confidence=null`，逐条件概率另入审计。

### 2.2 输入

- 两个通道共用 `ContentItem` 投影与同一份规范化图片（M3）。
- 分类有 `simple / precise` 两种互斥启用的模型判定模式，`llmPrompt` 与 `judgeConditions` 双份保留，切换不清空另一套数据；旧分类一律为简单模式。
- **简单模式**：`llmPrompt` 同时作为 LLM 判定描述、决策 `noul` 问句与 `choice` 选项说明，保持原行为。
- **精确模式**：只读启用且非空的原子条件。正向条件任一可靠成立即可支持，LLM 可综合多条弱证据；负向条件任一明确成立即否决且优先。至少一条启用正向条件才构成模型判定口径，只有负向条件不能判「属于」，也绝不回退 `llmPrompt`。
- 无当前模式判定口径的分类只走确定性条件。主分类组存在无有效正向条件的精确分类时，本次不问模型主分类，避免在残缺选项集上提前定案。
- **防注入**：抓来的标题、正文、图片只进 `state`（决策）/ user 消息的内容段（LLM），按不可信数据处理；模型判定口径只进 `instructions` / `criteria` / 分类清单。

### 2.3 判决链与生效

判定按档位依次运行，**每档跑出的结果全部落库**，生效结论由各档的「定案条件」决定：

1. **确定性**：永远运行（零成本），对全部分类给出命中 / 未命中。无当前模式判定口径的分类由它定案。
2. **决策模型**（总开关开且有可用供应商时）：对有口径的分类发 `noul`、对完整主分类组发 `choice`，一次请求打包，图只在 `state` 里放一份。
   - 简单是非：`p ≥ T_high` 定案为属于，`p ≤ T_low` 定案为不属于，中间为灰区不定案。
   - 精确是非：逐条件得 `p`；任一负向 `p ≥ T_high` 判否，全部正向 `p ≤ T_low` 判否，至少一正向 `p ≥ T_high` 且全部负向 `p ≤ T_low` 判是，其余为灰区。
   - 主分类：最高项概率 `≥ T_primary` 定案，否则不定案。
   - 内容带图而回答者是纯文本供应商：结果落库，一律不定案。
3. **LLM**（总开关开且有 provider 时）：只对上一档未定案的分类与主分类发请求；返回即定案。精确分类收结构化正负条件及组合规则。
4. **回退**：模型档都未定案的有口径分类，由确定性结果定案；主分类回退到确定性主分类。

模型定案后不回看确定性条件（关键词捞不回模型的「否」）。一档失败（HTTP 错误、超时、响应不符契约、解析失败）= 该档本次无结果，未定案项交下一档，不采纳半份答案。

### 2.4 落库

- `verdicts`：唯一键改为 `(subject_type, subject_id, category_id, rule_id, source)`，新增 `effective`。每个 `(主体, 分类)` 恰有一行 `effective=1`。直播与图文统一落「属于」与「不属于」。简单决策行的 `confidence` 存 `p`，精确决策行为 `null`；`evidence` 存确定性命中说明 / LLM 理由 / 决策回答者及逐条件结果。
- `primary_verdicts`：`(subject_type, subject_id, source)` 唯一，存选中分类（`0` = 其他）、冗余分类名、分布 JSON（仅决策）、`effective`。每个主体至多一行生效。
- 消费方只读生效行：规则匹配（经 `classify()` 返回值）、时间表、面板帖子标记。`get_content_audit` 返回全部行并带 `effective`。
- `content_audit.analysis` 记逐分类逐来源结果、主分类各来源结果、决策灰区项、两个通道的逐供应商尝试（标通道）、回显版本与被拦下的图片及原因；精确决策另记 `conditionResults`（分类 id、条件 id、方向、原文、概率、灰区分带、是否实际促成定案）。

### 2.5 决策请求形状

```jsonc
// POST <baseURL>/systemone   含图时带 TypeSafe-Danger-Zone-Images: true
{
  "model": "jev-1.14.0",
  "state": { "主播": "…", "标题": "…", "分区": "…", "画面": "<uuid>" },  // 图文：作者/平台/类型/引用/正文/配图[]
  "assets": { "<uuid>": { "type": "image", "format": "jpg", "data_base64": "…" } },
  "questions": {
    "c12": { "type": "noul", "instructions": "这条内容是否属于「歌回」？<简单模式判定描述>" },
    "c13:song-visual": { "type": "noul", "instructions": "依据 `标题`、`分区`、`主播`、`画面` 判断：画面有歌词或歌单。这一条是否成立？" },
    "c13:game": { "type": "noul", "instructions": "依据 `标题`、`分区`、`主播`、`画面` 判断：画面是游戏实况。这一条是否成立？" },
    "primary": { "type": "choice", "instructions": "这条内容最像哪一项？",
                 "criteria": { "歌回": "<简单描述或精确正向条件组合>", "杂谈": "<判定口径>", "其他": "不属于以上任何一项" } }
  }
}
```

- 每道题必须按请求的 id 与类型返回、数值在 0–1 内，否则整份响应判失败。
- `choice` 选项键是分类名（模型看得到），同名冲突时追加 `#id`；「其他」与分类名冲突时同样改名。
- 图片线格式首期只做 TypeSafe 原生 `assets`（base64 JSON）；OpenRouter / vLLM-SR 等把图放进 `state` 的格式，接入具体供应商时按其一手文档加选项。

### 2.6 运行参数（settings，面板决策模型卡）

| 键 | 默认 | 含义 |
|---|---|---|
| `decision_enabled` | 关 | 决策档总开关（判定链每次直读） |
| `decision_gray_low_pct` / `decision_gray_high_pct` | 20 / 80 | 是非灰区下界 / 上界（settings 存整数百分数，消费时 /100；保存时校验下界 < 上界） |
| `decision_primary_min_pct` | 60 | 主分类最高项定案门槛（同上，百分数） |
| `decision_request_timeout_ms` | 30000 | 单次请求超时 |
| `decision_circuit_threshold` / `decision_circuit_cooldown_ms` | 3 / 600000 | 单供应商连续失败熔断与冷却 |

供应商名单顺序即优先级：带图内容先试启用且就绪的 vision 供应商，都不可用再试纯文本供应商；无图内容按名单顺序。

## 三、图片管线

识图是两个通道的主路径，规范化在判定前统一完成，两个通道共用结果：

- **本地化**：图文配图已由 pipeline 落本地；直播在 `live_start` 判定前把关键帧（缺则封面）经带 Referer 的下载落本地。图床 URL 不直接交给任何模型。
- **规范化**（`sharp`）：按字节内容识别格式；动图取首帧；按 EXIF 摆正；统一输出基线 JPEG；长边 ≤ 1568，短边 < 280 时放大，极端长宽比放大后超限则补边；单图体积有上限。产出同时满足 Jev 门禁与 LLM 输入。
- **拦截**：解码失败或处理后仍不合规的图在本地丢弃，逐张记原因进审计；全部被拦即按无图判定。

## 五、验收口径

**M1**：名单增删改 / 启停 / 排序落 settings 并可撤销；key 明文回显仅限本机面板、撤销不落明文；探活失败 502 且错误不含 key；LLM 通道不受影响。

**M2 / M3 / M4（离线）**：`npm run typecheck`、`npm run build`、`npm test` 通过；以下路径各有用例：
- 决策关 / 无供应商 / 调用失败 / 解析失败 / 灰区 → 交 LLM；LLM 关或失败 → 确定性定案。
- 纯文本供应商对带图内容不定案；对无图内容可定案。
- 每个 `(主体, 分类)` 恰一行生效；主分类至多一行生效；直播判否落库。
- 坏图（WebP、GIF、过小、过大、超长图、损坏文件）被规范化或拦下并记原因，不会让请求整单失败。

**实战验收**：
- LLM：真流量下结构化输出失败率、带图请求确实携带规范化图片（直播与图文各至少一例）、内容记录可逐条回看各来源结论与依据。
- 决策档：p95 延迟、请求失败率（上线后 HTTP 400 应接近 0）、灰区比例（灰区与不定案过多则大部分流量仍回 LLM，按审计调阈值或换模型）。
- 四条回退路径不阻塞推送。
