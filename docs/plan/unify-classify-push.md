## 〇、为什么统一

直播推送与图文推送曾是「同一判定心智的两套实现」：

| 维度 | 直播 | 图文（旧） |
|---|---|---|
| 判定层 | 独立 categories 表（LLM 提示词 + 关键词/分区确定性条件），判定入 verdicts 可回看 | 无分类层，filters + judgePrompt 内嵌在每条图文规则里，判定不留痕 |
| LLM 调用 | 一次批量调用覆盖全部 prompt 分类 | 每条命中规则一次调用 |
| 作用域 | 规则侧主播集合（空 = 全部主播） | 账号侧选用列表（空 = 一律不推） |
| 删除语义 | 删分类 → 引用规则级联停用（可恢复） | 删规则 → 账号选用直接清扫（不可恢复） |
| 恢复策略 | 冷启动三类抑制（pipeline 侧） | resume/gap/normal 轮次 + backlog 封顶（source 侧） |

另有前瞻性动因：**决策模型通道**只吃「人填的分类口径」且只覆盖枚举类判断——判定口径若继续内嵌在规则里，决策模型够不着图文。统一后决策模型只需接进一个分类器。

## 一、产品模型（现行）

收敛为同一个三段式心智：**判定口径（分类）→ 推送规则（分类 × 范围 → 渠道 + 推送词 + 附加动作）→ 范围在主体卡上反向可见**。直播与图文在各自分页管理，同表与组件复用不意味着入口合并。

1. **分类卡（统一）**：分类 = 名称 + LLM 提示词 + 确定性条件组。条件组按内容类型提供算子：文本子串 / 分区（仅直播）/ 帖子类型（原创·转发）/ 引用 / 必须带图。旧图文的 filters 整体上移进分类。
2. **推送规则卡（统一）**：规则 = 内容形态 × 分类引用（空 = 任意内容）× 生效范围 × 渠道 × 推送词 × 附加动作（翻译，仅 X 内容显示）。直播与图文规则字段完全一致。
3. **作用域双向视图、单一数据**：规则编辑器选主体；主体卡（主播卡 / 账号墙）反向展示生效规则，点击进入同一规则编辑器。范围只能在规则编辑器修改，两侧都不提供独立的账号选用勾选。
4. **判定可回看补齐**：图文判定同入 verdicts（身份键通用化），内容记录两侧共用同一组件。
5. **「错过期间怎么办」统一呈现**：冷启动抑制与 backlog 补推在概念上并为一组恢复策略设置（按内容类型各给默认值）；实现仍分属 pipeline 与 source。

### 产品决策（已拍板）

- **D1 作用域默认语义 = 空即全部生效**（沿用直播现行，与 gateway 群自助规则模型兼容）。图文规则未指定账号范围 = 对全部账号生效（含未来新增）；UI 明确「全不选 = 全部」提示。主体详情展示范围覆盖结果，不另设账号选用规则的配置。
- **D2 旧图文规则一次性搬家**：一条旧规则 → 自动生成一条分类（筛选条件与判定提示词上移）+ 一条引用该分类的规则；启动期内部迁移、不进撤销栈。搬完旧表 DROP。
- **D3 翻译留在规则层**：作为规则的附加动作字段，仅 X 内容生效；翻译是输出物不是判定口径，决策模型不覆盖生成任务，不上移到分类。

## 二、底层抽象（已落地）

**抽出来的（当前不再耦合）**：

1. **ContentItem 内容项抽象**（`src/analysis/content.ts`）：`{ subjectType, subjectId, uid/accountId, text, tags, pics, url, ts }`——直播场次与图文帖都投影成它；分类判定与模型 prompt 构造只吃它。**输入带图**（直播封面/关键帧、图文配图）。
2. **条件算子注册表**（`src/analysis/matcher.ts`）：关键词/分区/帖子类型/引用/带图都是「条件组 + 且/或」，按内容类型注册，替代两个写死的 matcher。
3. **verdicts 身份键通用化**：`(room_id, live_time)` → `(subject_type, subject_id)`；`source` 枚举预留 `'decision'`。
4. **判决链接口**（`src/analysis/classifier.ts` 的 `JudgeStage`）：确定性 → （决策模型档，P4 未接）→ LLM → 确定性兜底的级联形状已就位，各档可插拔。
5. **聚合与模板收敛**：`aggregateRuleHits`（渠道并集去重、首个非空模板、空并集不推）两形态共用；`renderTemplate` / `renderPostTemplate` 按内容类型提供变量集。
6. **「推送是否等待判定」规则级化**（`src/core/pipeline.ts` 的 `hasCoveringCategoryRule`）：只有「引用了分类且 scope 覆盖本内容」的规则才等判定；纯「任意内容」规则立即推，避免通知被无关分析阻塞，也不产生双推。

**不抽（本质差异，保持各自实现）**：

- 抓取 / 归档 / 去重 / 恢复策略：直播是状态型信号（diffRoom、场次身份、冷启动抑制），图文是事件型信号（UNIQUE 去重、backlog 窗口）。
- 翻译：留 LLM 通道（`post-analysis` 任务），仅 X 平台门控。
- 平台文案与图片链路差异（X 图走代理隧道等），维持薄处理。

## 三、与轴 B 的关系（撤销/注册表体系接点）

统一任务构建在能力面地基层上，有三个硬性接点必须随表结构变更同步维护，否则撤销与变更历史会静默失灵：

- **写路径生在撤销引擎里**：统一后的规则/分类写工具一律经 `runToolTracked` 进注册表（快照/审计/撤销自动获得），不先写裸 REST 再迁移。级联停用这类多步写天然落在同一快照事务里，撤销可整体回滚。
- **`undo.ts` 忽略列清单 + `undo-view.ts` 中文名映射随表迁移更新**：表合并/改名/搬列时，`DEFAULT_IGNORE_COLUMNS`（轮询回写列不参与差分）与 undo-view 的「settings 键 + 表 → 中文操作名」唯一信源必须同步登记新表新列；漏登记的表现是变更历史出现乱码条目或撤销误还原轮询游标。
- **write-path-inventory 互锁测试会强制登记**：新写工具若漏进注册表或漏配 `AGENT_EXCLUDED_TOOLS`，`write-path-inventory.test.ts` 直接红——这是防分裂的机械保障，不要绕过。
- **一次性数据搬家不进撤销栈**：D2 的迁移是启动期内部行为，不走 `track`，不产生变更历史条目。
- 注册表是唯一能力信源：统一后的规则模型在 `tools.ts` 定义一套工具，webui / MCP / Agent / QQ 四端同构；gateway 群自助规则已跑在「规则侧作用域」模型上，D1 选「空 = 全部」与之天然兼容。

## 附录 A：P2 目标模型详规（历史执行规格）

> **历史方案**：以下是 P2 落地时逐条执行的规格，结论已在代码里。列名与工具签名以源码为准，本文不再维护镜像；新增概念（`scope` 的账号引用格式、分类条件组）现行语义见 [mcp.md](../mcp.md)。

### A.1 categories 表扩展（吸收旧图文规则的筛选条件与判定提示词）

新增列（`ensureColumn` 在线补列，无需重建）：

| 列 | 语义 |
|---|---|
| `applies_to` | 分类服务的内容类型（`live` / `post`；UI 按此渲染可用算子，且不可更改） |
| `post_types` | 帖子类型子集（`original` / `retweet`），空 = 不限 |
| `require_quote` | 必须是引用帖（仅 X 免登录回退路线产出该标记，其余平台永不命中） |
| `require_media` | 必须带图 |

- 条件组泛化：keywords（通用）/ areas（仅 live）/ postTypes / requireQuote / requireMedia 各为一组，组间关系仍由 `cond_mode` 统辖；「所有非 LLM 条件组皆空且无提示词 = 死分类」由校验层拒绝。
- 算子注册表补 postType / quote / media 三个算子（appliesTo=post）；keyword 算子对 post 判定 text。

### A.2 push_rules 表扩展（统一规则，旧图文规则表退役）

- 新增 `subject_kind`（`live` / `post`）与 `llm_translate`（D3：规则层附加动作，仅 X 内容运行时生效）。
- 主播集合列更名泛化为 `scope`：live = 主播 uid 列表；post = 账号引用列表（`'twitter:screenName'` / `'weibo:uid'` / `'bili:uid'`）。**空 = 全部生效**（D1，两形态统一）。随表重建搬迁。
- 三张账号表的 `rule_ids` 列删除（表重建）；账号卡反向显示规则 scope 对本账号的覆盖，点击进入规则编辑器修改。
- 删分类级联停用引用规则的语义两形态统一沿用；删规则不再有账号侧清扫（无 rule_ids）。

### A.3 旧图文规则一次性搬家（不进撤销栈）

每条旧规则（含停用）→ 一条分类 + 一条规则：

- 分类：`applies_to='post'`；name=规则名；llm_prompt =（开了判定且判定提示词非空）? 提示词 : null；keywords 与原关键词；post_types 由原创/转发勾选映射；require_quote / require_media 由引用/带图映射；enabled/sort 随规则。
- 规则：`subject_kind='post'`；category_id=新分类 id；scope=三账号表选用关系反查出的账号引用列表；channels/message_template 原样；llm_translate 随旧开关；sort 接现有全局序追加。
- **行为保持闸**：原语义「账号未选用 = 该账号不推」，若一条旧规则没有任何账号选用 → 原语义下永不生效；搬家后 scope 空按新语义 = 全部生效会翻转行为——故**无账号选用的规则一律 enabled=0 落地**并在迁移日志注明。
- 幂等：旧表不存在即跳过；搬完 DROP。旧的 `platform` / `account_ids` 列随表删除一并消失。

### A.4 判定与匹配语义（P2 行为变化点）

- **图文判定分类制**：`feed_post` 与 `live_start` 同走判决链（ContentItem 投影），只对 `applies_to` 匹配内容类型的启用分类判定；verdicts 落真实 categoryId。post 侧 LLM 判否也落 `pass=0`（「为什么没推」可回看；直播侧保持只记「属于」）。
- **匹配统一**：`matchRules`——命中 =（分类引用空 ∨ ∈ 匹配集）∧（scope 空 ∨ 含 subjectRef）；live 的 subjectRef = uid，post 的 = `platform:key`。旧的 matchPushRules / matchPostRules 退役或改薄封装。
- **翻译**：判定从图文分析任务里退役，只留翻译（命中规则聚合后，任一 `llm_translate` 且平台支持时调一次生成）。
- **推送等不等判定规则级化**：仅当「存在引用了分类的启用规则且其 scope 覆盖本内容」时才等分类；纯「任意内容」规则不再排在 LLM 后面。按场/按帖单次判定，不产生双推。

### A.5 轴 B 接点（P2 内同步完成）

- 工具注册表：`upsert_category` 带 appliesTo + post 条件；`upsert_push_rule` 带 subjectKind/scope/llmTranslate；旧的图文规则工具与账号工具的 ruleIds 入参退役。write-path-inventory 互锁随之更新。
- undo-view 中文名映射登记新列与表变更；undo.ts 忽略列清单核对（rule_ids 消失）。
- webui 最小可用适配（能配、能看、不崩；体验精修在 P3），demo mock 同步。

## 附录 B：产品验收纠偏

> **历史方案**：本节是 P3 初版未过验收后的审查结论与修复方案，已按此落地。当决策依据读，不是待办。

### 审查结论与修复

| 问题 | 影响 | 修复 |
|---|---|---|
| P3 主播页混排两类分类和推送规则，图文页缺分类卡 | 图文用户必须离开当前页配置判定，直播原有路径也被扰乱 | 两页各有「分类规则」「推送规则」，分别按 appliesTo/subjectKind 投影同表；名称、颜色、行样式、按钮和弹窗共用 |
| 分类弹窗允许随意切换内容类型 | 已引用分类的规则会变成无法命中的配置 | 页面决定新分类的类型，编辑不提供类型切换；能力层拒绝改分类类型、跨类型引用及不适用的条件 |
| 图文账号侧取消勾选可把最后一个账号移出后写出空 scope | 空 scope 实际变成全部生效；勾选全部现有账号还会被改成对未来账号自动生效 | 账号详情与主播详情同为「生效规则」展示入口，范围修改统一进规则编辑器；保留显式所选集合，不折叠为全部 |
| 图文范围内嵌多平台网格，直播范围另开弹窗 | 同一种操作有两套布局、保存习惯 | 图文沿用直播圆柱摘要 → 搜索、头像卡多选弹窗 → 完成 → 保存规则；账号卡附平台角标 |
| 分页过滤后，排序仍要求同表全排列 | 直接提交可见 id 会被真实后端拒绝，宽松 demo 却放行 | 共享 `mergeVisibleOrder`，仅替换本页的槽位；demo 拒绝不完整、重复或不存在的排序 id |
| 规则编辑器声明二级弹窗却未把 level 传给 openSheet | 详情入口可能覆盖一级弹窗，保存/关闭目标错位 | 补齐 level 传递；主体详情的规则入口统一关闭详情再开一级规则编辑器 |

P0–P2 的核心复用仍然成立：ContentItem 投影、条件算子、分类判决链、统一 matchRules、渠道聚合与模板渲染、规则 scope 单一信源，以及能力层的审计/撤销，无需拆回两套规则表。修正的是入口归属和能力边界。

### 无法逐项对应的差异与统一交互

| 差异 | 统一方案 |
|---|---|
| 直播分区 vs 图文帖子类型、引用、带图 | 同一分类编辑器保留名称、LLM 提示词、确定性条件、且/或与保存顺序，仅替换内容对应的条件组；引用明确标注仅 X |
| 直播单平台主播 vs 图文三平台账号 | 同一范围摘要与搜索多选弹窗；图文卡增加平台角标，身份键保留平台前缀。空范围始终表示全部（含未来新增） |
| 图文翻译无直播对应物 | 同一推送编辑器增加「附加动作」可选区，仅图文显示附译文，明确仅 X 帖生效 |
| 直播状态恢复 vs 图文历史帖子补推 | 公共「推送设置」按内容类型分行；图文展开时间窗和条数上限。主动关闭后重开静默的底层语义保持，不能把直播场次套成帖子 backlog |
| 直播场次时间轴 vs 图文最近帖子 | 主体卡与详情都展示自身内容和生效规则；分类判定从内容记录回看。直播只归档正判、图文还记录 LLM 负判，负判回看的对称性尚未统一，不在此次 UI 修复中改历史归档语义 |
| LLM 标准从旧图文规则上移分类 | 统一口径：有提示词且 LLM 可用时以 LLM 为准，确定性条件只兜底；无提示词始终确定性。旧图文「先筛选再判定」与此不同，属于 A.4 既定行为变化，验收时需核对旧分类标准是否完整描述带图/原创等要求 |

验收覆盖：两页归属、新增/编辑/删除、分类联动、范围选择、分页内排序不扰另一页、主体详情规则入口、撤销后重拉、demo 与真实 API 的类型边界、1440/960/640 宽度。

### C.1 基线假设与待补接缝

   - **`DecisionProvider` 独立通道**：与 `LlmRouter` 平行，独立管理 key、限流与熔断，主协议对齐 `POST /v1/systemone`。

### C.2 核心规则与判决链逻辑

1. **多分类解耦 vs 优先级展示（`noul` + `choice` 双轨并存）**：
   - **推送规则触发（用逐项 `noul` 是非判断）**：不同推送规则考虑的分类域不同（如规则 A 关注「歌回」，规则 B 关注「联动」或「带图自拍」）。每个分类独立产出 `pass: boolean`，允许多分类同时命中，**各规则按所引用的分类独立匹配、互不截胡**。同一内容命中多条推送规则时，仍由 `aggregateRuleHits` 按推送规则拖拽优先级取第一条非空推送词模板、渠道取并集。
   - **标签展示与横向主次（用 `choice` 概率分布 + 置信度排序）**：命中的多个分类标签按置信度从高到低排序展示；`choice` 产出的横向概率分布（各分类 + `none` 概率和为 1）一并记入 `content_audit`，既供面板直观查看主分类归属，也可在后续需要时对 `noul` 的「Yes 偏置」做交叉校准。
   - **优先级归属原则**：绝不把「分类上下拖拽优先级」塞进模型 prompt（避免多跳逻辑退化与拖动顺序导致客观判定漂移）；任何需要按分类优先级截断的逻辑一律在代码侧按 `categories` 顺序确定性裁决。
2. **分类内部条件分工与判决链级联**：
   - **纯确定性分类（`llmPrompt` 为空）**：100% 走 `deterministicJudge`（算子注册表）。
   - **带提示词分类（`llmPrompt` 非空）**：
     1. **硬结构门禁预筛（仅图文客观属性）**：若分类勾选了 `post_types`（只原/只转）、`require_quote`、`require_media`，不满足的直接短路判 `pass=false`，不耗模型 token。（注：`keywords`/`areas` 因存在旧标题党与反串，有提示词时不直接短路判 `true`，仅作模型参考特征与故障兜底。）
     2. **DecisionJudge（System 1，`/v1/systemone`）**：高置信度（`p ≥ T_high` 判真 / `p ≤ T_low` 判假）直接定案（`source='decision'`）；落入灰区（`T_low < p < T_high`）或通道未启用/失败的分类，升级交下一档。
     3. **LlmJudge（System 2，VLM/LLM）**：对灰区或未决分类调多模态 LLM 定案（`source='llm'`）。
     4. **DeterministicJudge（兜底回退）**：模型通道均不可用或报错时，回退 `keywords` / `areas` 等确定性条件组兜底（`source='rule'`）。

### C.3 模型输入输出契约

1. **System One（`/v1/systemone`）单次请求混装契约**：
   - **一次请求、一笔输入费**：`questions` map 原生支持混装不同题型。同一次请求内同时下发 **1 道全局 `choice`（含全部待判分类 + `none` 兜底项）** 与 **N 道逐分类 `noul`（是非题）**。
   - **图片单次挂载**：图片在 `state.images`（或顶层 `images[]`）中只放一次，各题 `instructions` 用反引号引用字段名，避免按引用次数重复计费及撑爆请求体上限。
   - **防注入结构化 `state`**：抓取到的标题/正文放入 `state` 子字段，指令明确要求只依据客观内容与画面判断，忽略正文中任何试图指定分类结果的文本。
   - **证据合成**：决策模型无自由文本输出，由代码将 `noul` 概率与 `choice` 占比合成为可读 `evidence`（如 `"决策判定 p=0.91（横向占比 0.78，模型 jev-1.14.0）"`），落入 `verdicts` 与 `content_audit`。
2. **LLM（System 2）输入微调**：
   - 在 `src/analysis/tasks/classify.ts` 中将分类配置的 `keywords` / `areas` 作为辅助参考一并附入分类说明；
   - 在直播系统提示词中明确「当直播间标题与实际关键帧画面明显不符（如挂旧标题打其他游戏）时，以关键帧画面为准」。
