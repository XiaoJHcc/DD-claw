# X/推特图文来源实施计划

> **状态**：P0–P3 全部落地（隧道 fetch / X 配置 / 连通性探测 / 独立分页 / 免登录源 / `x_accounts` 名单 / 图文推送分支 / 规则级 LLM）。
> **适用范围**：本文件保留决策依据、实现约定与验收条款。其中「独立图文规则表 `post_rules` + 账号 `rule_ids` 选用」的设计
> **已被统一计划取代**（现行：分类 `applies_to=post` + 推送规则 `subject_kind`/`scope`），相关段落标为历史；
> 现行契约见 [mcp.md](../mcp.md) 与 [统一计划附录 A](unify-classify-push.md)，机制细节见 [modules/](../modules/)，
> 进度见 [status.md](../status.md)。前置调研（含全部 [实测] 证据与待验证清单）见 [research/twitter.md](../research/twitter.md)。
> 目标：把关注的 X 账号推文作为**独立于 B站/微博**的图文来源，机械筛选（原创 / 转发 / 引用 / 带图）符合即推，
> 可选经 LLM 判定是否推，并依赖 LLM 翻译。**验收在 UI**：X 走独立分页（`#view-x`），全部设置在该页完成。

## 已定决策

1. **数据源：免登录路线**——`Nitter RSS 为主`（唯一能机械区分原创/转发/带图，[实测] 20 条 = 10 转 + 10 原创、19 带图），`x.com HTML + tweet-result 为备`（零第三方依赖，但实测拿不到转发）。多实例轮询 + 失败即弃。
2. **代理：面板可配，默认 `http://127.0.0.1:7890`**——落 `settings`（运行时配置唯一信源）；代理不可用必须**告警而不是静默**。
3. **UI：开独立分页「X / 推特」**——X 是独立于 B站的一条路径，基于开播设计的设置页几乎全不适用（审计见下），不该硬塞。
4. **账号模型：独立名单 `x_accounts`，可选关联到主播**——不要求 X 账号对应 B站主播（`Watase_Yuzuki` 这类日系声优本就不是）；关联仅用于展示与推送文案。
5. **共享配置：引用设置页的推送渠道与 LLM 供应商**，不在 X 页重复配置（settings 唯一信源）。
6. ~~**规则形态：X 页独立「图文帖规则」卡 + 独立表 `post_rules`，开播规则零改动**~~ **历史方案**：后续统一为「分类 + 推送规则」两表（分类承接筛选与判定提示词，规则承接范围/渠道/推送词/翻译），旧表一次性搬家后 DROP；现行见 [统一计划](unify-classify-push.md)。
7. **默认只推「原创」，不论有没有图**——落地为迁移生成的图文分类的确定性条件（帖子类型 = 原创），面板随时可改。
8. **LLM：判定 + 翻译，默认关**——判定口径从「规则级开关 + 判定提示词」上移为**分类的 LLM 提示词**，翻译保留为**规则的附加动作**（仅 X 帖生效）；LLM 关/熔断/失败 → 回退机械筛选照推。
9. **不做**：不发推 / 不点赞 / 不关注（只读）；不引入 Playwright 常驻浏览器；暂不接官方 X API 与付费第三方 API（绝不在轮询里"拉最近 20 条"）。

## 设置页对 X 的适用性审计（新分页的依据）

| 设置页现有卡片 | 对 X | 处置 |
|---|---|---|
| 监听卡（B站登录 / 监听动态 / 微博登录 / 抓取设置） | **不适用**：X 无登录态，非直播、非动态、非微博 | 不进该卡；间隔与代理放 X 页 |
| 分类 / 推送规则 | 语义不同（曾是开播专用） | 统一后两页各管自身内容类型，组件复用、入口分开 |
| 时间表 / 主播列表 | **不适用**（直播时间轴） | 不动；主播详情仅加一行只读的关联 X 账号 |
| NapCat / LLM 供应商 / 推送渠道 | **适用，必须共享** | 留在设置页，X 页只引用 |

结论：共享的三张（NapCat / LLM / 渠道）留在设置页，X 专属自成一分页；开播路径零回归。

## 分页骨架（已落地）

`#view-x` 是图文分页，X、微博、B站动态三条来源在此单墙混排（平台角标 + 筛选胶囊）：连接与 X 源设置、
关注账号卡墙（身份段 + 生效规则 + 帖子段）、分类规则卡、推送规则卡、最近帖子。具体控件与交互以 `webui/`
与 [modules/panel.md](../modules/panel.md) 为准，本文不镜像 UI 规格；仍成立的两条要求：

- **「测试」必须给可读原因**（`代理可达 · x.com 200` / `实例 403 Cloudflare` / `限流稍后重试`），不能只回 ok/fail——这是区分「我填错了」与「链路断了」的唯一手段。
- **「抓不到」与「没有新推文」必须在同一处可区分**。

## 数据模型与语义

- 名单表 `x_accounts`：`screen_name`（去 @、小写归一）/ 可选 `bili_uid` 关联 / 启停 / 增量游标 / 最近成功抓取 / 平台昵称与故障列。ID 与平台昵称**是平台事实不可手改**（昵称由添加时校验种入、抓取回写；换账号就删了重加）。
- **连接设置不建表**：代理地址、实例列表、间隔、回退开关都进 `settings`。
- **`posts.uid` 语义**：X 帖存 `screen_name`（`platform='twitter'`），微博帖存微博账号 uid，B站动态帖存 B站 uid——**归属 = 被抓账号自身**。「这条帖子属于哪个主播」由各名单的可选关联反查，不靠 uid 借位。
- **筛选条件已上移进分类**（`applies_to='post'` 的帖子类型 / 引用 / 带图 / 关键词条件组）；旧 `post_rules` 表与其 `platform` / `account_ids` 列是历史，已随统一计划删除。

## 实现约定（落地时确认、至今有效）

1. **RSS 的 `<guid>` 就是推文 id**，比解析 `<link>` 可靠；转发时 `guid` 与 `dc:creator` **都是原作者**——"同一推文被多次转发折叠成一条"因此是结构性事实，不是 bug（要「每次转发都推」见「未定问题」）。
2. **图片是实例代理 URL**（`http://<实例>/pic/media%2FXXX.jpg`）→ 一律还原成 `https://pbs.twimg.com/media/XXX.jpg` 存档：实例会死，CDN 形态才长期可用。
3. **回退路线的分工**：HTML 只用来"发现 id"（React Flight 载荷里 id 与正文配对不可靠），详情一律走单推接口；这条路**看不到转发**（`retweeted_status_results` 恒 null），用回退时「转发」条件永不命中——需要转发就得让 Nitter 活着。
4. **监听开关的 auto 判据 = 代理已配置**（不是"代理已验证可用"）：默认配置自带 `http://127.0.0.1:7890`，所以 auto 一开始就是开；源本身在名单为空、代理为空时不会起。
5. **`enabled` 必须被采纳**：新建账号时漏解析 `enabled` 会让 `enabled:false` 被静默忽略——面板与 MCP 共用同一套解析，改动时别只改一条。
6. **实例探活打 `/<user>/rss` 而不是首页**：首页挂 Anubis 不代表实例不可用（实测 `x.n0g.xyz` 首页是挑战页、RSS 却给 20 条）。判活口径必须与真实使用路径一致。
7. **链路可用性口径 = 能抓到推文**（实例可用，或免登录回退可用）：`x.com` 经代理瞬时不通只影响回退与图片下载，不该把主路线报成不可用；结论里如实注明原因（`probeVerdict`，CLI 与面板共用）。
8. **状态快照语义**：`GET /api/x` **只读快照，绝不打网络**（面板每分钟轮询）；快照**只描述已保存的配置**——弹窗里测未保存的输入值只在弹窗内显示，不写快照；配置真变了，相关旧结论作废（灰点 +「配置已改，请重新测试」），轮询间隔变化不影响任何连通性结论；未测试是 `checkedAt: null`（灰点），与"测了但失败"（红点）必须可区分。
9. **帖子去重与发送**：图文帖不走 `DecisionRule`（没有"场次"概念），去重由 `posts` 的 `UNIQUE(platform,item_id)` 兜住；图片必须落本地后交 NapCat（它拉不到 `pbs.twimg.com`），下载失败按无图发。

## 未定问题

- **「每次转发都推」**：Nitter RSS 的 link 指向原作者推文，按 link 去重会把同一推文的多条转发折叠成一条。要支持该语义必须另取 RT 自身 id；默认取折叠语义。
- **免登录路线的长期稳定性**：HTML 内嵌条数上限与高频账号漏推率、`tweet-result` 的 token 任意值是否长期有效，均未长期观测；接口静默失效时必须能被健康检查识别，不能读成「没发推」。

## 验收条款

1. `npm run probe-x` 能列出两条路线当天的推文，并正确统计转发/带图/最新时间；实例全挂时给出可读原因而非空结果。
2. UI 走完整链路：连接 → 测试 → 监听开关 → 添加账号（可关联主播）→ 配置图文分类与推送规则 → 最近帖子出现新推文 → QQ 群收到（带图推文带图）；不需要手改配置文件或数据库。
3. 关掉代理 → 只告警，**不产生「没有新推文」的静默假象**；恢复后自动继续。
4. **开播路径零回归**：设置页、时间表、主播列表行为不变；`npm run typecheck && npm test && npm run build` 全绿。
5. `npm run webui:dev` + `?demo=1` 下 mock 与真实后端同构；新增解析函数带单测（注入式 fetcher，模子 = `sources/weibo/feed.test.ts`）。

## 风险与纪律

- **时效性**：Nitter 实例随时死/限速、X 页面结构随时变（X 已向 Nitter 发停止函）。解析必须防御式，**空结果要区分「没有新推文」与「抓取失败」**。
- **单点**：代理挂 = X 源全停；实例挂 = 降级到免登录回退；两者都挂 = 告警。
- **微博已另有独立文档**：微博曾是主播的附属数据源，后升级为独立名单（[weibo-source.md](weibo-source.md)，已落地），两条链路同构，细节不在本文件。
- **法律定位**：低风险**非授权**渠道（违反 X 条款，可能被停止函/封号波及），不是合规方案；项目一贯只读、不写操作。
