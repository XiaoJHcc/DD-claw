# 文档维护

## 唯一信源与阅读层次

| 文档层 | 负责 | 不负责 |
|---|---|---|
| 根 `AGENTS.md` | 项目定义、架构边界、跨模块约束、模块入口 | 文件地图、实施进度、任务记录 |
| 各模块 `AGENTS.md` | 本目录设计要点、长期约束、代码职责地图 | 复制父级规则、逐次改动日志 |
| `design.md` | 设计理由、概念关系、目标与明确不采用项 | 手抄完整类型/schema、宣告实施进度 |
| `modules/*.md` | 深入机制、跨模块时序、排障与配置配方 | 再列一遍模块文件地图 |
| `mcp.md` / `content-audit.md` | 专题的现行使用与行为契约 | 执行日志、历史方案混排 |
| `status.md` | 实现状态、待验收项、尚未完成能力 | 复制代码分工或设计全文 |
| `plan/*.md` | 决策依据、实施规格、验收合同 | 冒充现行 API 或第二份进度总表 |
| `boundaries.md` / `research/*.md` | 外部能力边界、来源证据、实测坑与时效 | 内部代码地图 |
| 根 `README.md` / 本目录 `README.md` | 用户上手 / 开发文档导航 | 第二份架构与开发进度总表 |

## 维护纪律

- 修改事实所属的文档，其他入口用相对链接递进披露；少量导航摘要不复制细节。
- AGENTS 与现行设计/专题不追加日期型补丁、任务总结、分期执行日志、本机验收路径或测试计数。把有效结论融入对应章节，临时过程丢弃。
- 研究的基准日期、证据来源与已测版本属于可复核性，不当作临时日志删除；不要将有时效的外部结论写成永久保证。
- 计划明确哪些是历史方案、哪些验收尚未完成。被替代的实施指令不得继续作为待办；未完成合同、长期约束与不采用决策不能随日志一起删除。
- 实现存在不等于验收通过，尤其不得把未提交工作区代码升级成“已验收”。进度只在 `status.md` 汇总。
- 类型、SQL 列和全量路由以源码及契约测试为准，不维护必然漂移的镜像清单；文档说明概念和容易误解的语义。
- 尽量保持被代码或其他文档引用的路径与章节；改动时扫描引用并修复相对链接、锚点和归属说明。
