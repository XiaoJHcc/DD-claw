# 分析层：判决链、模型通道与匹配机制

`src/analysis` 回答两个问题：「这条内容属于哪些分类」（判定）与「按人填的规则该推给谁、推什么」（匹配）。前者的结论入 `verdicts`，完整过程入 `content_audit`；机械去重不在这里（见 [rules/AGENTS.md](../../src/rules/AGENTS.md)）。逐文件职责与长期不变量见 [analysis/AGENTS.md](../../src/analysis/AGENTS.md)。

本页是**现行实现机制说明，不代表验收**：验收结论、未完成能力与进度只查 [status.md](../status.md)。

## 判决链

一次判定回答两件事：每个分类「属不属于」（是非，允许重叠，推送规则只看它），以及主分类组里「最像哪一个」（主分类，展示用）。契约全文见 [plan/decision-model.md](../plan/decision-model.md)「二」。

确定性条件永远先跑（零成本）；有判定描述的分类再按模型档位顺序判，每档只收到上一档**未定案**的分类，返回 `null` = 本档不可用。链是档位表而不是 if-else 堆叠，新增判定方式只加一档、不动编排。

| 来源 | 何时定案 | 产出 |
|---|---|---|
| 确定性 | 无判定描述的分类；模型档都未定案时的回退 | 条件组命中 / 未命中，`source='rule'` |
| 决策模型 | `p ≥ 上界` 或 `p ≤ 下界`（灰区不定案）；带图内容只由纯文本供应商回答时一律不定案 | `source='decision'`，`confidence` = P(属于) |
| LLM | 有 provider、总开关开，返回即定案 | 结论 + 理由，`source='llm'`，不带置信度 |

**每档跑出的结论都落库**，`effective` 标出每个分类唯一生效的那一行；取用方只读生效行，其余行留给回看。LLM 不输出置信度：它自报的数字没有校准意义，概率只来自决策模型。

有判定描述的分类不做确定性预筛：关键词、分区与帖子属性只作故障兜底。标题党与反串太常见，命中关键词不代表内容真是那个分类。

- **模型档权威**：模型给了否定结论后再被关键词捞回来，等于模型判断白做，所以模型定案不回看确定性条件；回退只发生在模型**不可用**（无 provider / 开关关 / 调用失败 / 解析失败）时。
- **无条件组的分类不落确定性行**：那里没有可回看的判据；只有当它在模型不可用时成为生效结论（判否）才落一行说明原因。
- **主分类**：模型档定案优先；都没有时按分类排序取组内第一个「生效且属于」，都不属于记为「其他」。

## 输入面：`ContentItem`

直播场次与图文帖被投影成同一个 `ContentItem`：身份键、作者、正文、标签、视觉输入、链接、时间。判决链、prompt 构造、条件算子都只吃它，所以新增内容形态（弹幕、预告）时只需扩投影，不动判定逻辑。

标签的语义是刻意的：

- `type` 在投影时折叠成 `original` / `retweet`——三个平台各自的转发枚举（含 B站 `DYNAMIC_TYPE_FORWARD` 的归一）在 source 侧统一，matcher 只认这一个值。
- `isQuote` 是三态：`true` / `false` / **`unknown`**。只有 X 的免登录回退路线能判定引用，其余来源不知道不等于没有——按「未知按未命中」处理，这是旧 quote 语义的延续。
- `hasMedia` 决定视觉判定是否有输入；`platform` 决定文案措辞、quote 语义与翻译门控。

视觉输入面统一是规范化后的 JPEG Data URL：直播用关键帧（缺则封面），图文用配图。**图床 URL 不能直接交给模型**——B站图床缺 Referer 会 403，X 图墙内不可达；所以判定前先由 pipeline 落本地（直播的取图在判定那条 promise 里做，不挡任意内容规则的推送），再经规范化，分析层只消费结果。

## LLM 任务契约

一次判定把所有待判的有描述分类**合并成一次调用**：每个分类一条清单项（id、名称、判定描述）；有主分类组时再附一段单选清单（含 id=0「其他」）。输出 `{results:[{id, match, evidence}], primary?: {id, evidence}}`。合并而非逐分类调用，是为了成本与降级语义都保持最简——要么这次调用成功覆盖全部，要么整体回退。

解析对**完整性、id 唯一性、主分类 id 在选项集内**是硬约束，违规即整单判失败；模型编造的未知分类 id 丢弃。`maxTokens` 随分类数扩展——长清单被截断会稳定表现为「结果不完整」。

## Provider 层

- **路由由名单推导**：provider 名单顺序即优先级；text 路由收全部启用的，vision 路由只收多模态的。请求带图即走 vision，无图走 text；显式指定路由可覆盖。
- **双协议**：chat-completions 与 responses（system→instructions、结构化输出走 `text.format`）。Anthropic `/messages` 明确不接。
- **结构化输出三档**：`schema`（约束最强）/ `object`（只保证是 JSON）/ `none`（不带 response_format，解析时剥代码围栏兜底）。本地小模型与不支持的端点靠第三档活。
- **两级失败语义不同**：传输层可重试失败（网络 / 超时 / 429 / 5xx / 正文不是合法 JSON）在 provider 内就地重试并轮换 key；任务层 schema 不符不重试，直接记熔断、降级到下一个 provider——重试同一个模型对「确定性不听话」没意义。
- **缺 key 不是配置错误**：loopback 端点视为无鉴权；其余端点无 key 标「缺 key」跳过。这让「本地 LM Studio + 云端备用」可以共存。
- **工具对话的模拟降级**：端点不支持原生 tools 时，用提示词让模型输出一个 JSON 再由我们拼成工具调用。这不记熔断（不是端点故障），但参数同样过能力层校验——模拟路径不是绕开 schema 的后门。
- **含图但无就绪 vision provider 时剥图降级走 text**：硬着头皮带图会让整单在空路由上失败，把本可成功的纯文本判定一起拖死。

## 决策模型通道

判决链的**第一档**：一次 `POST <baseURL>/systemone` 同时回答是非（每分类一道 `noul`）与主分类（一道 `choice`）。
代码分工：线格式与名单 / key 在 `decision-providers.ts`，候选顺序 / 熔断 / key 轮换在 `decision-router.ts`，
请求打包与解析在 `tasks/decide.ts`，档位在 `classifier.ts`（`JUDGE_STAGES = [decisionJudge, llmJudge]`）。

- **候选顺序**：含图内容先试「启用且 `vision`」的供应商（名单序），都不可用 / 失败再试纯文本供应商；
  无图内容按名单序。纯文本供应商的请求里既没有 `assets`，`state` 里也没有图片 ref。
- **定案条件**：`p ≥ 上界` 或 `p ≤ 下界` 定案，中间是灰区（结论落库、不定案）；主分类最高项
  `≥ 主分类门槛` 才定案。带图内容只被纯文本供应商回答时，结论落库但**一律不定案**（它没看图）。
- **失败语义**：HTTP 错误 / 超时 / 响应不符契约 = 该供应商本次失败（计熔断、换下一个），
  全部候选不可用则本档没有结果，未定案项交 LLM；灰区与「没看图」不算失败。
- **独立通道**：名单在 settings `decision_providers`（含 `vision`），key 在 `decision_key:<name>`，
  总开关 `decision_enabled`，超时 / 熔断与灰区门槛在 `decision_*` 运行参数；与 LLM 的
  `llm_providers` / `llm_key:*` / `llm_enabled` 互不共享，也不复用 `LlmRouter` 的熔断状态。
- **门槛调参**：阈值是 settings 里的可调参数（面板决策卡「高级」），按线上审计回看调整；
  常见症状是灰区过多——大部分流量仍回 LLM，届时先调阈值再考虑换模型。
- **审计**：`content_audit.analysis` 记逐供应商尝试（`channel='decision'`）、响应回显的模型版本、
  灰区项，以及决策档被跳过 / 失败的原因（`stageNotes`，与 LLM 的 `fallbackReason` 分开记）。
- **模型版本看响应回显**：测试与审计都用响应里的 `model`（别名会漂），不用请求里写的字符串冒充实际回答者。

`/v1/systemone` 的请求/响应细节、候选模型与硬约束见 [research/decision-models.md](../research/decision-models.md)；协议选型、分期与判定验收合同见 [plan/decision-model.md](../plan/decision-model.md)。

## 视觉输入规范化

图片在送模型前统一处理（`image-prep.ts`，依赖 `sharp`），因为单张坏图会炸掉整单（Jev 只收 280–1568px 的静态 PNG/JPEG，服务端不缩放）：

1. **按内容解码**：不看扩展名；动图（GIF / 动态 WebP / APNG）只取首帧。
2. **摆正与去透明**：按 EXIF 方向旋转像素，透明区铺白底。
3. **尺寸**：长边压到 ≤ 1568；短边不足 280 时等比放大，极端长宽比放大会越界时改为补白边。
4. **输出**：基线 JPEG，超体积逐级降质；产出自检不合规即拦下。
5. **拦截记录**：解码失败、下载失败、超张数或压不下来的图逐张记进 `content_audit.analysis.skippedImages`；全部被拦按无图判定。

LLM 与决策模型共用同一份产出，所以门禁按两者中更严的一方（Jev）定。

## 分类草稿试判

分类浮窗可直接用未保存草稿试判。面板先从既有直播场次 / 图文归档按主体、时间和数量随机抽取**带源图**的记录，只回内容摘要与一张缩略图源地址，不调用模型；用户再对当前 `subjectId` 列表发起复测，后端按原顺序精确读取同一批样本，复用 `ContentItem` 投影与图片规范化，分别运行确定性条件、LLM、决策模型。与正式判决链不同，试判的三档彼此独立，不做降级裁剪，便于对照每一档的属于 / 不属于、决策概率与灰区；模型未配置、开关关闭或失败只影响对应档位。

试判模型调用与正式分析共用 `AnalysisQueue`，使用当前 provider、开关和门槛。结果只存在本次响应中，不写 `verdicts` / `primary_verdicts` / `content_audit`，也不触发推送；真实内容的审计回看仍只记录正式处理过程。X 缩略图经仅允许 `pbs.twimg.com` 的受限反代读取，沿用代理与缓存目录边界，不开放通用图片代理。

## 规则匹配

匹配是纯确定性函数，可以离线推演，也因此是「为什么推了 / 为什么没推」最可靠的解释面。命中条件的定义在 [analysis/AGENTS.md](../../src/analysis/AGENTS.md)，这里只记设计取舍与算法：

- `scope` 为空表示全部（含未来新增），取舍是「不为新账号反复改规则」；同理分类引用为空表示任意内容。
- 多条规则同时命中时**叠着用**而不是互相取消：渠道取并集、推送词取排序后首个非空，于是「一条泛规则兜底 + 一条分类规则加权」能共存。
- 没有内置兜底规则——「任意内容 × 全部主体」规则就是旧全局默认的等价物，需要的人自己建一条，避免沉默的默认行为。
- 条件算子按内容类型注册，组间关系由且/或统辖；无有效组不命中，防止纯提示词分类被确定性路径误判成恒中。
- 模板变量按定义序替换：直播 `{liver}`（原名优先，缺省回退简称）/ `{uname}` / `{title}`；帖子 `{author}` / `{screenName}` / `{text}` / `{url}` / `{liver}`（关联主播）。

## 翻译

翻译是规则层的附加动作，只对需要翻译的平台出现（当前仅 X），由命中规则聚合后的「任一条开了翻译」触发，每次推送最多调一次。失败原因进 `content_audit.translationWarning`，用户能看出「这条本该有译文」。

## 排障

- **判定没跑**：只有 `live_start` 与 `feed_post` 会进判定；`title_change` / `live_end` 不烧模型。`feed_post` 没有可用分类（`applies_to` 不匹配）时直接返回空。
- **判定结果为空但分类看着该命中**：看 `content_audit.analysis.results` 里该分类的各来源行（生效行 + 非生效行）的 `evidence`（模型理由 / 「确定性条件未命中」/ 回退说明）与 `fallbackReason`（为什么模型档没接手）。
- **模型一直回退**：看 `attempts` 里每个 provider 的 skipped / failed 原因；`缺 key` 与 `熔断中` 是两种不同处置（补 key vs 等冷却）。
- **带图判定失败**：确认 vision 路由是否有就绪 provider（无则已剥图降级），以及图片是否被门禁拦下（`skippedImages`）。
- **两条规则都命中却只推到一个渠道**：渠道是并集，检查两个渠道是否指向同一个 QQ 目标。
- **判了「不属于」还想知道原因**：直播与图文的判否都落 `pass=0`，在内容记录里按分类分组回看。
