# DD-claw 项目设计

本文描述长期目标、架构理由与产品边界。代码职责见各目录 AGENTS，实现状态见 [status](status.md)，深入机制与专题入口见 [文档索引](README.md)。

## 1. 目标

监听用户选定的 B站直播间，以及 B站动态、微博、X 独立账号名单，持续归档原始内容，判断内容分类，并按用户填写的推送规则路由通知。关注列表是监听候选池，不代表自动监听全部关注。

「阿梓唱歌才推送」是需求实例，不是系统目标。抓取、追踪、分析、偏好执行、通知需分别可替换，承载更多内容形态而不让来源或渠道理解用户语义。

### 规模假设（决定设计）

| 项 | 量级 / 性质 | 架构推论 |
|---|---|---|
| 关注主播 | 上百位 | 同步关注作为候选池，监听名单持久化管理 |
| 高峰同时在播 | 30+ | 批量检测；昂贵分析排队，不进入轮询循环 |
| 信号 | 持续状态，不只是一次性事件 | 原始数据按领域归档，可供后续分析反复使用 |
| 偏好 | 每主体若干条条件 → 动作 | 人填分类与推送规则，确定性执行，不依赖 LLM 解释偏好 |

### 目标分层

- 基础：匿名批量检测开播状态，按规则推 QQ / 本机通知。
- 规模化：登录后同步关注、归档动态与微博；X 通过代理独立接入。
- 内容理解：分类与多源上下文，逐步扩展到预告提取和直播中状态判断。
- 交互：本机面板与受控 Agent 接入共享能力面，不另造业务逻辑。

## 2. 核心判断：这是一个自然语言融合问题

标题和分区只是先验。主播可能一直挂着游戏区，动态却预告稍后唱歌，弹幕已经出现歌名与叫好；只看单一字段不足以可靠判断内容。因此模型负责融合互相矛盾的内容证据，而不是代替人决定通知偏好。

| 信号 | 定位 |
|---|---|
| 标题、分区 | 便宜、可结构化，但可能陈旧 |
| 弹幕 | 目标中的实时观众反馈，按需采样而非全员常驻 |
| 动态、微博 | 预告和临时安排，需要登录凭据 |
| 画面 | 关键帧 / 封面提供辅助语义；含图任务须走支持图像的路径 |
| 音频 | 非主路径，不因此引入录播或声学分析系统 |

文本融合是主线，不等于忽略已有图片。输入有图就使用多模态能力；没有图才用纯文本模型。分类效果与输入来源是否就绪是两件事，不能把未接入的弹幕等信号当成现有上下文。

## 3. 技术选型

| 层 | 选择与理由 |
|---|---|
| 语言 / 运行 | TypeScript、ESM、Node.js ≥22；面向 Windows / macOS 本机常驻 |
| 持久化 | `better-sqlite3`，同步领域仓储与事务，单进程本地数据 |
| 调度 | 自有 `PeriodicTask`，串行周期执行与停止控制，不引入额外调度框架 |
| 模型调用 | 原生 fetch，provider 路由、熔断、多 key 与双协议适配；不引入独立 LLM 网关 |
| QQ / 本机通知 | NapCat OneBot 11 HTTP；Windows Toast 与 macOS 原生 helper |
| WebUI | 原生前端 + 构建期内嵌，发布工件与后端同版本，不引入第二套应用框架 |

依赖版本以 `package.json` / lockfile 为准。外部方案评估见 [research](README.md#研究与外部证据)，明确不采用的方案统一在 §11。

## 4. 架构

项目有两条正交轴：**运行时数据流**（从抓到推）和**能力面与接入**（查数据、改设置的入口）。交点是 SQLite：领域表保存内容与判定，`settings` 保存运行时配置。

### 轴 A — 运行时数据流

```text
sources → 领域归档 + Signal 总线 → core/pipeline
                                      ├─ 内容分析（有界队列）→ verdicts
                                      ├─ 机械去重 / 冷启动策略
                                      └─ 确定性规则匹配 → PushMessage → notify
```

直播是持续状态，帖子是离散事件；两者共享分类与规则模型，但来源事实、归档、去重、恢复语义分别处理。归档先于推送抑制，静默不等于丢历史。

| 解耦点 | 边界 | 扩展方式 |
|---|---|---|
| Signal | 抓取 → 编排 | 新来源实现 source，不知道模型与通知 |
| 任务化模型接口 | 分析任务 → provider | 任务定义输入与结构化输出，provider 负责协议与路由 |
| PushMessage | 决策 → 通知 | 新渠道实现 Notifier，不理解分类与偏好 |
| 能力注册表 | 业务能力 → 接入 | 能力在 `tools.ts` 定义，各入口适配执行 |

### 分类与推送的产品模型

人类需求是唯一锚点信源，直接以结构化形式落地，不做 NL → 结构化编译。

- **分类**：用户填写提示词与确定性条件，`applies_to` 区分 live / post。无提示词永远走确定性；有提示词使用已启用的模型判断路径，模型不可用或失败时保留确定性回退。模型只判断内容，不解释偏好。
- **推送规则**：`subject_kind` 区分内容类型；分类引用为空表示任意内容，`scope` 为空表示全部主体（含未来新增）。图文非空范围使用带平台前缀的账号引用。
- **匹配结果**：各命中规则独立生效，渠道并集去重，推送词按规则排序选取首个非空模板。不以模型润色人工模板。
- **等待关系**：仅覆盖本内容的分类规则可以让推送等待分类；任意内容规则即时生效，后续判定不能制造双推。
- **翻译**：规则级附加动作，仅 X 帖使用；不可用或失败不挡推送。
- **界面投影**：直播页与图文页管理自身类型的分类 / 推送双规则，复用组件但不混合入口；主体只展示生效规则，范围在规则编辑器修改。交互约束见 [WebUI](../webui/AGENTS.md)。

图文账号与主播名单解耦。旧 `post_rules`、账号 `rule_ids` 只属于迁移历史，不是另一套现行规则模型。迁移依据保留在 [统一计划](plan/unify-classify-push.md)。

### 冷启动、补推与推送时机

状态机如实产生信号与冷启动标记，不做通知政策判断。直播启动时已在播的 first_run / restart_recovery 共用 `notify_on_first_run`，默认只追踪；新增监听与运行期实时开播分别处理。

图文补推按中断意图区分：主动关闭后的恢复轮始终静默；重启、崩溃、登录态中断与添加账号前的内容默认不补推，开启补推后受时间窗与每账号最新条数双重封顶；正常轮新帖不受补推上限影响。所有轮次都归档。精确轮次定义与默认值以 `core/backlog.ts` 为准，机制见 [数据专题](modules/core.md)。

用户规则管“谁、什么、去哪”，pipeline 管“何时”。未来只考虑增加式时机（等封面、换标题、实际内容变化），不引入静音或“不推”偏好。机械去重、防抖与冷却不做成用户偏好开关。

### 轴 B — 能力面与接入

```text
src/mcp/tools.ts（schema + handler + role）
  ├─ Web UI REST /api/*
  ├─ MCP over HTTP /mcp
  ├─ WebUI Agent（进程内 loop）
  ├─ MaiBot 插件（外部仓库，经 /mcp）
  └─ NapCat QQ 直连（OneBot 事件 → 进程内 loop）
```

能力层定义角色，接入层确认身份，模型产生的参数不可信。所有入口共享注册表的校验、审计、权限与可撤销写执行，不允许传输层绕过能力面改配置。

`/mcp` 永远要令牌，不设回环豁免；gateway 的渠道身份由服务端绑定与注入，读写范围隔离。详细安全与调用域契约只在 [MCP](mcp.md) 维护，方案依据见 [接入计划](plan/agent-access.md)。

### Pipeline：唯一的装配点

信号编排在 `core/pipeline`，跨模块实例与热生效回调在 `src/index.ts`。两者不能混为新的“大调度器”：前者串接领域处理，后者管理依赖生命周期。

领域归档、冷启动抑制、分析、机械去重、匹配、派发分别有明确归属。source 不做通知政策，状态机保持纯函数。分类与发送过程通过 [内容记录](content-audit.md) 留下标准快照、判断依据和发送结果，便于追溯而不是临时打日志。

### 全员开播检测：一个批量接口，不是逐个轮询

`get_status_info_by_uids` 每批 50 个 uid 分片。150 个关注只需每轮 3 次请求；不为每位主播建立独立状态轮询器。接口层集中封装，来源可替换。

### 高峰并发的关键：分析不入轮询循环

轮询只拉批量状态、diff 产信号；内容分析进入有界队列。无关分类不拖慢任意内容规则推送。结果缓存、同房间多触发合并与优先级属于扩展点，不因规模假设提前实现全部机制。

### 弹幕 WS 的定位（待启动）

按需拉起，不全员常驻：发现开播且需要分析 → 建连与采样 → 进入分析上下文 → 下播关闭。WBI、WS、触发与上下文聚合的实现状态只见 status。

## 5. 目录结构

根 [AGENTS](../AGENTS.md#按目录阅读) 导航到各模块 AGENTS，后者是代码职责地图的唯一文档信源。`docs/modules/` 只讲深入机制，不再复制逐文件职责。`webui/` 是前端源，`scripts/` 负责构建及平台辅助，`data/` 存放本地库与缓存。

## 6. 关键数据结构

不在设计文档复制 TypeScript / SQL 定义，字段以实际类型、schema 与契约测试为准。核心关系如下：

| 概念 | 语义 / 源码入口 |
|---|---|
| LiveStatus / Signal / LiveEvent | 平台事实、变化信号、直播快照；`src/core/types.ts`。直播场次以房间和开播时间标识；轮播不算直播 |
| ContentItem / Classification | 分析归一内容及分类结果；`src/analysis/content.ts`、`types.ts`。只有命中结果进入分类返回值，图文判否也可落档 |
| Source / LlmTask | 来源生命周期、任务化输入输出；`src/sources/types.ts`、`src/analysis/types.ts` |
| Category / PushRule | 人填分类口径与确定性动作；`src/core/push.ts`。live/post 不得跨类型引用分类 |
| PushMessage / Notifier | 通用通知载荷与执行接口；`src/core/types.ts`、`src/notify/types.ts`。priority 是预留字段，不代表已有优先级产品能力 |
| Scope / Undo / Chat | 调用域绑定会话、权限与撤销栈；`src/core/undo.ts`、`chat-store.ts` 和 `src/mcp/run-tool.ts` |

### 数据库领域关系

| 表群 | 回答什么问题 |
|---|---|
| `room_state`、`live_sessions`、`live_segments` | 当前事实、重启基线、历史场次与标题分段 |
| `follows`、`streamers` | 关注候选池与用户选择的监听名单 |
| `posts`、`snapshots` | 可反复分析的原文与媒体引用 |
| `categories`、`push_rules`、`push_channels` | 分类口径、通知需求、执行目标 |
| `verdicts`、`notify_log`、`content_audit` | 判断结果、派发记录与完整过程快照 |
| `x_accounts`、`weibo_accounts`、`bili_accounts` | 独立图文名单、抓取恢复状态与账号故障 |
| `settings` | 运行时配置唯一信源 |
| `undo_changes`、`chat_sessions`、`chat_messages` | 调用域内的可撤销变更和对话历史 |

存储细节见 [数据专题](modules/core.md)。预告时间表是目标概念：需保留来源帖、原文、计划时间（可空）、置信度与 upcoming / done / cancelled 状态，按阈值消费，不引入人工确认队列；未建结构见 status。

## 7. 成本分层

成本决定组合方式，不是实现进度表：确定性条件最便宜，是无提示词分类的独立路径，也是模型失败的兜底；多源文本与已有画面提供语义证据；更贵的判断不得侵入来源轮询。

缓存可在内容无显著变化时复用结果；队列可按触发合并与优先级调度。二者均是留缝，不是当前行为保证。决策模型通道尚未接入（`decision` 档位与 `source` 枚举只是预留），接入方案待另行制定；研究证据见 [decision-models](research/decision-models.md)，验收状态只见 status。

## 8. 里程碑

这里只定义目标与验收，实施进度见 [status](status.md)。

| 里程碑 | 目标 | 验收要点 |
|---|---|---|
| M1 基础通知 | 批量状态、机械去重、QQ / Toast | 运行期开播通知可达，真实通知链路验证 |
| M2 规模化与分类 | 关注同步、名单、凭据、归档、分类与判定留档 | 上百位稳定轮询，高峰分析不阻塞无关通知，误判依据可回看 |
| M3 预告时间表 | 历史时间轴、预告提取、预告条与到点推送 | 来源可追溯，时间与置信度入库、阈值过滤 |
| M4 偏好与路由 | 确定性匹配、可选增加式推送时机 | 规则正确、去重稳定、过程可回溯；优先级须先定产品方案 |
| M5 产品化 | 本机面板、多来源、受控多入口 | 完整流程可运维，接入权限与调用域隔离 |

## 9. 风险登记

| 风险 | 应对 |
|---|---|
| 平台风控、接口变动 | 保守轮询、必要请求头、集中接口封装；证据见 boundaries / research |
| cookie 泄露 / 失效 | 不进日志与版本库，建议小号；心跳识别失效并告警，不伪造成功 |
| 模型额度耗尽 / 服务失败 | provider 熔断降级、多 key、确定性回退 |
| 模型误判 | 标准与 evidence 快照可回溯，用户可调整分类口径 |
| 高峰分析积压 | 有界队列；未来按需合并与优先级，不承诺未实现机制 |
| QQ 通道不可用 | 独立本机通知；NapCat 小号与受控托管 |
| 接口资料失效 | 保留必要实测证据，不在项目大量摘录外部接口清单 |

## 10. 待定项（显式留缝，实现前再定）

| 问题 | 当前倾向 | 影响面 |
|---|---|---|
| 直播中抽查触发 | 定时 + 弹幕突变，依赖弹幕来源 | analysis / pipeline |

## 11. 已放弃 / 不采用（防止再被当待办）

旧计划与研究中的下列方向不得被重新当成待办：

| 项 | 原因 / 替代 |
|---|---|
| `PushDirective` | 解耦边界就是 PushMessage，中间态无价值 |
| 用户护栏：静音名单、静默时段、定时推、“不推”偏好 | push_rules 已表达需求；未来只增加推送时机 |
| `ntfy` | 本机通知 + NapCat 覆盖定位 |
| `signals` 全量表 | 有用数据进领域表，不为总线信号另建归档 |
| `analyze` / `notify` 主播开关 | 无消费者，遗留列不代表可用产品开关 |
| `preference_clauses` | 被结构化 push_rules 替代并删除 |
| LLM 文案润色 | 使用人工模板 |
| Anthropic `/messages` | 仅采用 chat-completions / responses |
| coding 订阅反代 / agent CLI 当模型后端 | 封号与合规风险；用官方 API，不用订阅反代 |
| 额外 LLM 网关、纯 Python 单体、平台大封装库 | 现有 provider 与 TS 模块足够，不增第二常驻层或无必要运行栈；接口集中封装 |
| 自动读取已登录 Chrome / Edge cookie | ABE 与安全边界；使用用户主动登录 / 导入 |
| CDP 直挂日常 Chrome | 新版默认 profile 不支持该远程调试方式 |
| 全员弹幕 WS 常驻 | 按需拉起，避免连接与 token 维护成本 |
| 完整录播、人工确认队列、公开部署 | 定位为个人短采样、无人管线、本机自用 |
| OCR 服务、音频声学确认、原画截图 | 非项目所需，不因外部能力可行而扩张范围 |
